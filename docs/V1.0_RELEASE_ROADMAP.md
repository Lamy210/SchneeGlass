## 1. 目的と対象

Finderを開かず、任意の実フォルダの内容をデスクトップGlassから安全・快適に扱う、macOS 15以降の長時間常駐ネイティブアプリ。v1.0 は機能数ではなく、日常使用、復旧、互換性、実測性能、配布の検証可能性で判定する。

既存のnon-destructive契約を維持する。user-owned source Move/Rename/Delete、silent overwrite、unknown staging auto-delete、権限外mutationは0件。ユーザーFilesystemがsource of truth。Finderは独立したアクセス手段であり、Glass表示やキャッシュはauthorityではない。新規クラウド、Runtime AI、private API、Full Disk Access、Accessibility Permission、network entitlement、Developer ID/Apple notarization は対象外。既存Ad-hoc配布のGatekeeper制約を明示する。recursive folder copy、deep drop、plugin framework、自動更新、SQLite移行は別ADRと採否判断を要し、v1.0必須ではない。

## 4. v1.0 Definition of Done

- 既存File Safety/Architecture/Public Repo guards、変更Swift strict format、package tests、macOS 15 compatibility、canonical Debug/Release、関連Visual snapshots、ASan成功。TSan/CodeQLは対象HEADまたは同一候補の関連コードに対する実行証跡を確認し、未解決の重大指摘なし。
- 全P0/P1項目は完了または明示的な仕様縮小により受入条件を更新してレビュー済み。重大なデータ損失/破損・起動不能・復元不能・操作対象誤り・権限逸脱・配布物不整合は未解決0件。
- macOS 15/26の実機QAにてclean install、Gatekeeper、通常使用、sleep/wake、external drive、display切断、終了/再開、旧バージョンからのupgrade、Recovery。OS/build/architecture/commit/ZIP checksum/resultを記録。未検証architectureは対応と断言しない。
- 500-item snapshotは既存ceiling worst < 0.5sを維持（CI条件）。追加目標は実測前の仮説: 1/4/8 Glass、各0/500/501 regular files（使い捨てlocal SSD fixture）、8時間常駐、sleep/wake 10回。安定起動後、無操作・外部変更なしの60秒warmup以降に1秒間隔でprocess CPU（100%=1 core）/RSS/FD数を記録、idle CPU中央値1%以下を暫定目標とする。別区間でFSEvents burst/外部volume/表示切替を計測。crash/hang 0・access acquire/releaseの不均衡0をテスト/診断で確認し、peak RSS/FDと持続増加を調査。実機の機種・CPU・RAM・OS build・candidate SHA・測定時間・sample countを記録し、閾値はbaseline取得後にレビューで確定する。根拠なしにPASSとしない。共有runner値を実機SLOに転用しない。
- 配布はADR-0011を遵守。既存公開buildより単調増加、exact candidate provenanceと実機QAを結合、公開物のchecksumとread-back成功、既存Release/タグの上書きなし。更新失敗時は前版の案内と設定復旧手順（無条件downgrade保証ではない）。
- 新規SLO、対応OS/CPU、権限、配布方針の変更は別レビュー。QA未実行をPASSとしない。macOS 15/26の実機/VM可用性とCPU architectureは先に棚卸しし、未検証組合せは明記。対応範囲縮小は明示判断・利用者向け文書更新・互換性影響レビューが必要。

## 6. 仕様レビュー・完了判定の運用

状態は Proposed / Ready / In Progress / Verified / Merged / Released を区別する。各IDに責任者、追跡Issue/PR、対象commit、検証コマンドまたは実機QA記録、結果、残リスクを対応付ける。実機が必要な項目は環境未確保なら Blocked。必須CIの未完了や実機QA未実施はVerifiedにしない。

P0/P1の延期を単なるチェック外しで認めない。scope変更は理由・ユーザー影響・代替/リスク・確認者・再評価時期を個別PRでレビューする。非破壊契約・File Safety・既存公開物の上書き禁止・配布由来検証は延期不可。既存release docsの旧Developer ID記述は歴史的記録として区別し、新しいoperator導線には混ぜない。

### R03の追加受入条件: 連続リリースと一貫した証跡

現行`materialize-public-release-build-history.sh`は一般公開Releaseの`RELEASE_EVIDENCE.txt`を優先し、存在しなければ固定済みlegacy manifestに限りBUILD_INFOを受理する。現在のad-hoc candidate BUILD_INFOをそのまま新公開Releaseに付けるだけでは次回のhistory検証で拒否される。旧notarized schemaに架空のApple公証情報を入れて回避してはならない。

- ad-hoc public evidence schema、version/build/source SHA、tag解決先、candidate/公開ZIPのSHA-256、owner QA、run/artifact ID、distribution typeを区別し、公開後のhistory consumerと一緒に設計する。
- 旧Releaseの履歴検証を弱めず、legacy/旧notarized/ad-hocの各schemaを明示的に分岐する。ad-hoc公開後に同じものを履歴として取得し、次の高いbuildだけ受理するround-trip fixtureをpublisher実装前に用意する。
- schema欠損、別tag/source、偽のnotarized metadata、既存番号再利用、history overflow（#537）、履歴の出力先競合を拒否する。history出力のfinalizeは既存destinationへ入れ子移動することも禁止。
- この設計/fixtureは公開操作なしでレビューする。実行権限が必要なpublisherの有効化と公開は別の段階。

既存docs/ADRが仕様の基準。OpenSpecは未導入のため本PRでは新しい依存/ルールを追加しない。導入する場合は既存規約と衝突しない最小PoCおよび個別提案（proposal/design/specs/tasks、既存ADRへの参照、仕様二重管理禁止）を先行し、既存Issue/PRを置き換えない。

各PRで現状・目的・範囲外・受入条件・検証・指摘の真偽・残存リスクを記録。コード変更では旧実装で失敗し新実装で成功する回帰テストを優先する。CIと実機QAの未完了、管理者権限不足、課金・資格情報、破壊的変更の場合は該当操作のみ保留する。

本計画は仕様提案であり、実装完了・v1.0公開・既存Issueのcloseを意味しない。
