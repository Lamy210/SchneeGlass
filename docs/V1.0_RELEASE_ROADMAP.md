## 1. 目的と対象

Finderを開かず、任意の実フォルダの内容をデスクトップGlassから安全・快適に扱う、macOS 15以降の長時間常駐ネイティブアプリ。v1.0 は機能数ではなく、日常使用、復旧、互換性、実測性能、配布の検証可能性で判定する。

既存のnon-destructive契約を維持する。user-owned source Move/Rename/Delete、silent overwrite、unknown staging auto-delete、権限外mutationは0件。ユーザーFilesystemがsource of truth。Finderは独立したアクセス手段であり、Glass表示やキャッシュはauthorityではない。新規クラウド、Runtime AI、private API、Full Disk Access、Accessibility Permission、network entitlement、Developer ID/Apple notarization は対象外。既存Ad-hoc配布のGatekeeper制約を明示する。recursive folder copy、deep drop、plugin framework、自動更新、SQLite移行は別ADRと採否判断を要し、v1.0必須ではない。

### R03の追加受入条件: 連続リリースと一貫した証跡

現行`materialize-public-release-build-history.sh`は一般公開Releaseの`RELEASE_EVIDENCE.txt`を優先し、存在しなければ固定済みlegacy manifestに限りBUILD_INFOを受理する。現在のad-hoc candidate BUILD_INFOをそのまま新公開Releaseに付けるだけでは次回のhistory検証で拒否される。旧notarized schemaに架空のApple公証情報を入れて回避してはならない。

- ad-hoc public evidence schema、version/build/source SHA、tag解決先、candidate/公開ZIPのSHA-256、owner QA、run/artifact ID、distribution typeを区別し、公開後のhistory consumerと一緒に設計する。
- 旧Releaseの履歴検証を弱めず、legacy/旧notarized/ad-hocの各schemaを明示的に分岐する。ad-hoc公開後に同じものを履歴として取得し、次の高いbuildだけ受理するround-trip fixtureをpublisher実装前に用意する。
- schema欠損、別tag/source、偽のnotarized metadata、既存番号再利用、history overflow（#537）、履歴の出力先競合を拒否する。history出力のfinalizeは既存destinationへ入れ子移動することも禁止。
- この設計/fixtureは公開操作なしでレビューする。実行権限が必要なpublisherの有効化と公開は別の段階。

### R03-01: ad-hoc公開証跡 contract（実装前提案）

次の版から自己整合する公開履歴を作るため、旧Apple公証用`RELEASE_EVIDENCE.txt`とは**異なるファイル名・型**の`ADHOC_RELEASE_EVIDENCE.json`を候補とする。これは実装済みschemaではない。公開可否を単独で証明するものでもない。

公開assetの最小セット（提案）: `SchneeGlass-X.Y.Z-adhoc.zip`、`SHA256SUMS`、`BUILD_INFO.txt`、`ADHOC_RELEASE_EVIDENCE.json`。内側candidate ZIPの**bytesを変更せず**公開名へ変更し、公開名のmanifestを新規生成する。candidate BUILD_INFOは候補検証用（github-adhoc-candidate）として保存し、公開側BUILD_INFOには公開用distribution（github-adhoc）を明記する。候補と公開物のmetadataを混同しない。Apple公証用証跡を同時に作成しない。診断ファイルは公開assetに含めない。

| JSON field（全必須） | 制約・独立した検証元 |
| --- | --- |
| schema_version | JSON整数 1、未知schemaは拒否 |
| distribution | github-adhoc 固定 |
| repository_id | canonical repository IDの10進文字列、認証APIと一致 |
| tag, version | vX.Y.Z / X.Y.Z、相互一致・公開tagの実際のGit ref解決先を検証 |
| bundle_identifier | io.github.lamy210.schneeglass 固定 |
| bundle_build | 1〜9桁の正の正規10進文字列、候補metadata・公開BUILD_INFOと一致 |
| source_sha | 40桁lowercase hex、exact candidate commitと公開tagのcommitに一致 |
| run_id, run_attempt, artifact_id | 10進文字列の正ID、attemptは1固定。公開前に既存認証APIで確認 |
| outer_artifact_sha256 | 64桁lowercase hex、認証Actions artifact digest（outer ZIP） |
| inner_zip_sha256 | 64桁lowercase hex、候補ZIP再hash・owner QAと一致 |
| public_zip_name, public_zip_sha256 | 公開版名、再hash、SHA256SUMS、inner_zip_sha256と厳密一致 |
| qa_comment_id, qa_owner_id, qa_approved_at | #520の認証済みowner comment ID/owner ID/API作成UTC時刻、既存QA validatorと同一候補にbinding |
| code_signature, apple_developer_id_signed, apple_notarized | adhoc / JSON false / JSON false。notarization_id等を含めない |

IDとbuildは文字列として扱い整数変換の丸め・overflowを回避。JSON最大サイズを16 KiBの暫定上限としUTF-8・object一個・重複key・未知key・欠落・型違いを拒否する。時刻はUTC形式および有効な暦日時を検証。ZIPのbytesが一致しなければ再QAが必要。

#### 証跡producer / consumerを分離する

1. **Publication preflight:** exact current main、required CI、認証run/outer artifact、inner archive、実機QA・owner comment、governance、公開build/tag空き確認を既存helperで実行。証跡は検証済みvalueだけから組み立てる。timestampやQAをAI/CIが捏造しない。
2. **Publication read-back:** 手動承認後、create-only tag/draft、asset upload、assetのread-back hash/source tag確認、immutable Release公開の順序を別実装で設計する。公開前後に省略のない検証を要求し、部分失敗を成功扱いしない。証跡自身のhashを同一証跡に埋め込む循環依存は作らない。
3. **Historical consumer:** 認証APIで全非draft Releaseを取得。legacy tagはpin済みmanifestの経路を優先し、別のevidenceを追加してpinを回避させない。他tagは確定したad-hoc JSONまたは旧notarized textのどちらか一方だけを受理する。両方存在・未知・欠落・破損はfail closed。実際のGit tag ref（annotated tagならcommitまで解決）、公開asset/digest、該当Releaseのimmutabilityを確認する。検証済み各schemaから内部の`schema_version=1 / bundle_build=N` comparator入力を生成する。内部正規化ファイルを公開証跡と誤認しない。
4. **Time boundary:** historical consumerは当時の公開元commitを検証し、最新mainとの同一性を要求しない。Actions artifactは14日で失効するため、過去Releaseの履歴検証をexpired artifactの再downloadに依存させない。公開時に認証済みQA decisionとcandidate digest等をimmutable evidenceへ保管し、後日commentが編集/削除されても過去build番号をhistoryから除外しない。履歴が検証不能なら次回公開を停止する。immutable evidenceも人が実機QAを実施したことの独立証明ではない。

#### 実装順・必須テスト

- R03-01a: JSON parser/validator、public ZIP名・manifest・digest binding、fixtureのみ（GitHub書込なし）。[#541](https://github.com/Lamy210/SchneeGlass/pull/541)で実装・回帰テスト追加、CI未確定。実装で公開ZIP上限を暫定1 GiB、BUILD_INFOを既存10項目の公開用distributionへ明示、manifestの小文字hexとLF終端を必須とした。これは履歴Consumerの認証や実機QAを代替しない。
- R03-01b: legacyを固定、schema dispatch、live tag/assetを検証するhistory consumer。未対応schemaのfallback禁止。
- R03-01c: v0.2/build 3の仮想公開後にartifactがexpired/mainが進んだ状態でもhistoryを読め、次のbuild 4のみを受理、3/2を拒否。dual schema・tampered ZIP・tag置換・mutable Release・missing legacy・0件履歴・巨大数字・重複key・不正owner/ID・output競合をnegative fixtureにする。
- R03-01d: 上記のfixtureと既存File Safety/CI成功後にcreate-only publisherを設計・実装。実際のtag/Release作成は禁止のまま。

将来、GitHub側の履歴削除まで完全に検知することは現在のlist APIだけでは保証できない。immutable policyと既知legacy pinを維持し、必要なら公開履歴のappend-only記録を別途検討する。

既存docs/ADRが仕様の基準。OpenSpecは未導入のため本PRでは新しい依存/ルールを追加しない。導入する場合は既存規約と衝突しない最小PoCおよび個別提案（proposal/design/specs/tasks、既存ADRへの参照、仕様二重管理禁止）を先行し、既存Issue/PRを置き換えない。

各PRで現状・目的・範囲外・受入条件・検証・指摘の真偽・残存リスクを記録。コード変更では旧実装で失敗し新実装で成功する回帰テストを優先する。CIと実機QAの未完了、管理者権限不足、課金・資格情報、破壊的変更の場合は該当操作のみ保留する。

本計画は仕様提案であり、実装完了・v1.0公開・既存Issueのcloseを意味しない。
